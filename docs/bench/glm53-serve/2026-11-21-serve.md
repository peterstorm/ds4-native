# GLM-5.3 served: `ds4n-glm53-serve` behind Maya (2026-11-21)

Phase 4 of [the plan](../../plans/2026-11-19-glm53-native.md). GLM-5.3 full (753B, kitaniai's
UNCENSORED-MXFP4) answers OpenAI requests on the desktop's `:8000` as the fifth primary,
`glm-native` (served id `glm-5.3-uncensored-native`). This report covers what was built, how it is
proven, what it measured through the real server, and the one bug the end-to-end run found.

Commits on `glm53/engine-core`: `1849006` (serve), `26ea3db` (Sessions fix + distill), `6866989`
(`min_lost` 16). Deployment: `.dotfiles` `1ef77094` + `55d87bf2` (launcher, switcher, Pi, runbook
`scripts/inference/runbooks/glm53-native-runbook-2026-11-21.md`, contract `tests/glm53-native-contract.sh`).

## 1. Shape

```
Pi / any OpenAI client ──HTTP──▶ Maya serve/server.py (MIT, b3fa99ec + keepalive patch)
                                   renders GLM-5's template, tokenizes, parses reasoning/tool calls,
                                   queues requests, streams
                                     │ stdin/stdout: Maya's engine protocol (core/wire)
                                     ▼   GEN / STOP / WRAP / QUIT  →   INFO, READY, PP, T, STAT, DONE, ERR, NOTE
                                 ds4n-glm53-serve --serve        (src/tools/glm53_serve.cu, shell)
                                     │
                                 engine/glm53/conversation       (shell: one request on the Decoder)
                                     │  plan ← core/glm53/sessions (pure)
                                     ▼
                                 engine/glm53/decoder            (two GPUs; Experts from NVMe + RAM tier)
```

- **Protocol.** The engine speaks the same lines as DS4.1's `ds4n-serve`, so Maya needs no change:
  `INFO engine=ds4-native engine_kind=ds4-native model=glm-5.3 context=… vram_slots=… ram_records=…
  lambda=… checkpoint_gb=… load_s=… logit_bias=1 lanes=1`, then `READY <context> stop` (one lane:
  Maya queues the rest). Each GEN reports its prompt with `PP` lines, each token with `T`, a `STAT`
  every 8 tokens, and `DONE`. `NOTE` lines tell Maya's log what happened to the conversations
  (`[maya] sessions: set aside …`).
- **stdin** is read with `poll`/`read(2)` into a line buffer, so a `STOP` that arrives mid-reply is
  seen after the next token. GENs that arrive during a reply queue in order, and `WRAP` is sticky for
  the rest of the request (closes an open reasoning block). `QUIT` or EOF ends the engine after the
  request in flight.
- **Failures.** A prompt that is empty or does not fit is `Refused` before anything runs. Logits that
  are not finite fail that request alone (`Failed`): its conversation is dropped, the engine stays
  sound. A Decoder (CUDA) failure throws: the caches and Slots may no longer agree, so the engine
  writes the failure and exits 2. Maya starts it again at the next request (~80 s).

## 2. Conversations kept between requests (`core/glm53/sessions`, pure)

Maya sends each request's **whole** prompt. The engine keeps what earlier requests left, so a prompt
reads only its new tokens:

- the **live Session**: the tokens whose KV rows the caches hold;
- **Checkpoints**: Sessions set aside in host RAM (a copy of their rows, 95.2 KB a token), least
  recently used first, within a byte budget (`--checkpoint-gb`, 4 GB ≈ 42K tokens).

`plan(prompt)` is a pure function of the held Sessions and the prompt, returning a `Resume`:

1. Resume from the held Session sharing the **longest prefix** (the live one unless a Checkpoint
   shares strictly more), keeping at most all but the prompt's last token (its logits start the reply).
2. **Set the live Session aside** only when the prompt drops at least `min_lost` of its tokens and
   no Checkpoint already holds them. A chat's next turn re-renders the last reply and may differ in a
   few of its last tokens: that is the same conversation, not worth a copy. Another conversation
   taking the caches drops all of this one's tokens.
3. A **restored Checkpoint is freed only if the prompt continues it** (drops fewer than `min_lost` of
   it). One the prompt branches from (a different conversation sharing a system prompt or the
   template's start) stays held and counts as recently used.
4. A Checkpoint whose tokens another starts with holds nothing more, and goes; past the budget the
   least recently used go.

The shell (`Conversation::resume`) performs a Resume in a fixed order: **save** the live rows →
**restore** a Checkpoint's rows → **rewind** the caches to `keep` → **free** the host rows named.
Then it sweeps the prompt's rest (one `Decoder::prefill`) and writes the reply, telling `fed()` each
token, so `live()` always names exactly the rows the caches hold.

**Tests** (`tests/core/glm53/test_sessions.cpp`): named scenarios plus a randomized model of the shell
(a `FakeKv` that performs each Resume) checked against properties after every step: reuse is the
longest held prefix; the rows the caches hold are exactly `live()`; nothing is lost that no prompt
dropped; a restored Checkpoint is freed iff continued, otherwise gone only by budget eviction; the
budget holds. 300 seeds, `min_lost` 1–4, **17,097,424 assertions**. Mutation probe
(`mutate_sessions.sh`): 12/12 killed.

## 3. KV rows to host and back (`Decoder::save/restore/rewind`)

`HostPositions` holds positions' rows of a layer (its cache rows, the MLA latents, and on a Full
layer the indexer's keys) in pageable host memory; over every layer that is 95.2 KB a position. `rewind(n)` drops positions past `n` (no copy). The gate
is **bit-exactness**: a conversation restored from a Checkpoint must continue exactly as if it had
been read again.

`ds4n-glm53-serve-check` (receipts `2026-11-21-servecheck.{out,err}`, 4K context, λ 0):

| check | result |
|---|---|
| S1: A swept alone, then A restored and B swept / fed a token at a time / A's first third restored | logits exact (0 of 15,488,000 values differ, each) |
| S2: a server's conversations (X, Y, X's next turn from its Checkpoint, X's turn after from the live caches, a STOP) | every logits row and token equal to reading on empty caches (0 of 929,280 differ) |
| total | **0 of ~46.5M logits differ** |

## 4. The tokenizer in Maya's form (`tools/glm53-serve/write_tokenizer.py`)

Maya loads a llama.cpp-style tokenizer (`vocab.json` with token types, merges, special ids,
`chat_template.jinja`). The exporter mirrors llama.cpp's GLM converter:

- vocabulary padded to the model's 154,880 rows with `[PAD n]` tokens (type 5);
- added tokens marked special or shaped `<|…|>` are CONTROL (3); `<think>`, `<tool_call>`,
  `/nothink` and the like are USER_DEFINED (4, so they split the text like words); the rest NORMAL;
- pre-tokenizer `glm5`; special ids as GGUF keys (eos 154820, eot 154827, eom 154829, bos 154822),
  so Maya treats every stop id as an end of turn;
- Maya serves its own `glm5_chat_template.jinja` (`clear_thinking` defaults to false: past reasoning
  stays in the prompt, so a next turn is an append).

`--check MAYA_DIR` compares Maya's `Tokenizer.from_dir` with HF `tokenizers` on 36 texts (prose,
code, numbers, CJK and other scripts, every special, and chats rendered by both templates): **28,223
ids, 0 differ**. Mutation probe: 5/5 killed (pre `qwen35`; merges reversed, shuffled, sorted;
specials typed normal). `--install` runs this check every time it writes the tokenizer.

## 5. Measured through Maya (desktop, 64K context, λ 0.03, 2026-11-21)

Receipts: `2026-11-21-maya-e2e-engine.err.txt` (the engine's stderr: every line of three server runs),
`2026-11-21-maya-e2e-responses.jsonl` (the responses' usage, timings and answers). Load: 79–83 s,
83 Slots per Sparse layer, RAM tier 37–38 records per layer.

| request | prompt | reply | Expert reads |
|---|---|---|---|
| first chat, cold | 30 tokens in 14.3 s | 67 at **6.81 tok/s** | 9.9% missed VRAM; 46 from NVMe a token |
| 4,519-token document + question | 4,509 read in 22.9 s (**197 tok/s**) | 399 at **6.23 tok/s** | 12.9% missed (29 RAM tier + 48.5 NVMe a token); 134 of 160 ms a token waiting |
| reasoning, effort high | 55 read in 10.1 s | 366 at **7.05 tok/s**, `reasoning_content` parsed | 11.8% missed |
| chat X, next turn X2 | 102 of 114 reused, 12 read in 3.1 s | 28 at 5.9 tok/s | |
| Y (other conversation) | X set aside (141 tokens) | 49 at 7.2 tok/s | |
| back to X (X3) | **resumed 141 of 149**, 8 read in 2.2 s | 69 at 6.3 tok/s | |
| D, then C sharing 10 template tokens, then D2 | D set aside (44); C restores 10 from it, D stays held; **D2 resumed 44 of 52** | 3 each | |
| client disconnects mid-stream | | engine **cancelled** after 39 tokens | |

The answers are correct (101 + 103 + 107 = 311, 311 prime, Copenhagen → Stockholm, Jupiter).

**Reading the numbers.**

- **Decode is the NVMe.** At the 4.5K reply, 598 Expert picks a token, 12.9% missing VRAM: 48.5
  Experts (0.97 GB) read from the store a token, 7.2 GB/s effective. 84% of the token's time is
  waiting on reads. This is the plan's corrected decision 3 measured end to end: λ 0.03's ~6–7 tok/s
  through the server equals `ds4n-glm53-decode`'s 6.85.
- **Short prompts cost seconds whatever their length.** A sweep reads every Expert any of its tokens
  routes to: 27 new tokens touch nearly as many Experts as a few hundred (3–6 s warm, 14 s cold).
  Long prompts amortize it: 4,509 tokens at 197 tok/s.
- **Reuse is what makes it usable.** A next turn reads 8–12 tokens instead of the conversation. A
  conversation displaced by another comes back from its Checkpoint at the cost of a host copy.

## 6. The bug the end-to-end run found

The unit properties held for the planner as first written, yet in the first server run a third
conversation lost the second. The sequence:

1. X runs, then Y (sharing the first 10 tokens of GLM's template) sets X aside.
2. The next prompt shares only those 10 tokens with X's Checkpoint and more with nothing else. The
   planner restored X's Checkpoint for its 10 tokens **and freed it**, as if the prompt continued X.
3. X's next turn found nothing held: it read the whole conversation again.

The property that should have caught it ("nothing is lost that no prompt dropped") was stated about
the live Session only. The fix (`26ea3db`) frees a restored Checkpoint only when the prompt drops
fewer than `min_lost` of its tokens; otherwise it stays, moved to most recently used. The checker
gained the property "a restored Checkpoint is freed iff continued, otherwise gone only by budget
eviction", with scenarios for branching early from a Checkpoint and for a Checkpoint resumed from
counting as recently used.

**Lesson:** a cache-reuse planner's unit properties must cover every place state can leave, not only
the obvious one. A real client's shape (template prefixes shared by unrelated conversations) found
what synthetic prompts with random prefixes rarely produce.

## 7. `min_lost`: 64 → 16

`min_lost` decides when a dropped tail is "another conversation" rather than "this conversation's
re-rendered last reply". Measured through Maya's GLM-5 template: the re-render differs from the
cached tokens in **0** tokens (Maya renders with `clear_thinking` false and the same template). At
64, short exchanges (D's 44 tokens) were never kept apart, so switching back read them again. At 16
they are kept; a conversation of fewer than 16 tokens is ~1–2 s to read again. (`6866989`.)

## 8. Pi's GLM guard on this id

Pi's GLM guard sends `chat_template_kwargs.clear_thinking: true` and a `thinking_token_budget` to
tuned GLM builds, and `glm-5.3-uncensored-native` matches its `/uncensored/` rule. Under Maya both
are inert: Maya forwards only `enable_thinking` and `reasoning_effort` from `chat_template_kwargs`
and reads no `thinking_token_budget`. Maya's own `thinking_budget` (8192, the launcher's config)
bounds the reasoning, and past reasoning stays in the prompt, keeping next turns pure appends. If
clear_thinking were honoured, every new user turn would drop the last reply's reasoning: a save of the
live conversation as a Checkpoint plus a re-read of the reply, each turn. The guard test pins the
profile and says why (`.dotfiles` `pi/extensions/glm-guard/guard.test.ts`).

## 9. Open

- **Task quality** (Phase 5): CyberGym subset and a harm rubric against the Flash primaries;
  λ above 0.03 only after task benchmarks.
- **Speed levers**, in order: the second NVMe in `M.2_3`/`M.2_4` (decode and cold prompts are
  read-bound; `--store A,B` is ready); more host RAM (the owner's call); MTP once reads are cheap.
- **Lanes.** One request at a time. A second lane needs a second set of caches; with 83 Slots per
  layer already traded against 64K of context, it is a VRAM decision, not code.
- The `glm-5.3-cyber-native` Backbone serves (`WEIGHTS=cyber`) but is no primary, and has not been
  measured through the server.
- **No Ledger yet.** The Decoder sizes its Slots from free VRAM after every other allocation, not
  from Ledger arithmetic (DS4.1's rule). Reproducible in service because the launcher requires idle
  GPUs (three launches: 83 per layer each); `--slots-per-layer` pins it by hand. Plan, Phase 4.
